# Internationalization (i18n)

> **Status:** draft. Covers `lib/language/i18n/i18n.ts` and `lib/language/translations/`. See [Theming](./theming.md#direction-ltr--rtl) for how direction relates.

Uses `i18next` + `react-i18next`, with three languages: `en`, `ar`, `fr` (`fallbackLng: 'en'`).

## Language detection and persistence

```ts
detection: {
  order: ['cookie', 'htmlTag'],
  lookupCookie: 'lang',
  caches: ['cookie'],
}
```

The active language is detected from a `lang` cookie first, falling back to the HTML tag's language, and any language change is cached back into that same cookie.

**This is a separate cookie from direction.** [`DirectionProvider`](./context-providers.md) persists `ltr`/`rtl` under a `dir` cookie, entirely independently of `lang`. That means switching the UI language to Arabic does **not** automatically flip direction to RTL unless something else wires the two together — not seen yet in any batch. If your team expects "select Arabic → the whole UI flips RTL" as a single action, that connection needs to exist somewhere (likely a language-switcher component we haven't seen) rather than happening implicitly from the i18n config alone. Worth confirming rather than assuming.

## Translation files

`lib/language/translations/` exports `en`, `fr`, `ar` plus a combined `translations` object, with `TranslationKey` derived as `keyof typeof translations.en` — meaning **English is the source of truth for which keys exist**; TypeScript won't catch a French or Arabic file missing a key that only English has, only the reverse (using a key that doesn't exist in English at all).

## A curious detail: SSR branching in a Vite SPA

`i18n.ts` has a `typeof window === 'undefined'` branch that initializes i18next differently for a server context. Nothing else we've seen so far indicates this app does SSR (`main.tsx` uses `ReactDOM.createRoot` directly, TanStack Router's client-side `RouterProvider`) — this may be defensive boilerplate carried over from a template/starter rather than functionally reachable code in this project. Not worth documenting as "how SSR works here" unless a future batch shows otherwise.
